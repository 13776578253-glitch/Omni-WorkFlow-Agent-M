## 1 概要设计

本项目基于现有代码仓库实现，采用“手机端轻交互 + 服务端集中处理”的前后端分离架构。手机端以前端应用形式运行，负责页面展示、多模态输入采集、任务交互和本地缓存；服务端负责工作流处理、语音转写、历史管理、用户配置管理以及模型能力接入。系统围绕“输入采集 - 工作流处理 - 结果展示 - 历史沉淀”这一主链路展开，适合移动办公与任务处理场景。

### 1.1 处理流程

系统处理流程分为逻辑流程和数据流程两部分。

#### 1.1.1 逻辑流程

用户进入系统主界面后，可通过顶部导航切换到首页、工作流页或历史页。用户在首页或工作流页中发起任务，可选择文本输入、文件上传或语音录入等方式提交内容。手机端完成输入采集后，通过接口将数据发送至服务端，服务端完成工作流处理、语音转写或任务生成后，将结果返回给前端展示，并同步更新当前会话和历史记录。

**图1 逻辑流程图（建议绘制）**  
`主界面进入 -> 选择任务入口 -> 文本/文件/语音输入 -> 服务端处理 -> 返回结果 -> 保存会话/历史`

#### 1.1.2 数据流程

数据流程主要表现为用户输入数据在手机端采集、缓存、上传，再由服务端处理和存储，最后回传至前端界面展示。对于普通文本与文件输入，数据在一次请求中即可完成处理与返回；对于长音频任务，系统采用异步任务处理方式，通过状态查询持续同步任务进度。

**图2 数据流程图（建议绘制）**  
`用户输入 -> 前端采集与本地缓存 -> API上传 -> 服务端处理与存储 -> 响应前端展示`

### 1.2 总体结构设计

系统总体结构可分为四层。

第一层为手机端表现层，负责首页、工作流页、历史页和用户页面的展示与交互。  
第二层为前端业务与本地缓存层，负责页面状态管理、会话缓存、历史缓存、文件上传、录音控制和接口调用。  
第三层为后端接口与业务处理层，负责认证、工作流处理、历史记录管理、用户偏好管理、门户数据管理和任务状态维护。  
第四层为数据与模型服务层，负责 PostgreSQL、ChromaDB、本地模型服务及云端模型服务的接入与支撑。

**图3 总体结构模块架构图（建议绘制）**  
`手机端表现层 -> 前端业务与缓存层 -> 后端接口与业务层 -> 数据与模型服务层`

### 1.3 功能设计

系统功能设计围绕五个核心模块展开。

1. 主界面导航与任务触发模块：负责首页、工作流、历史三类页面切换，并通过首页能力项、录音入口和新建工作流操作触发任务处理。  
2. 工作流处理模块：负责组织用户输入、AI 响应、会话内容展示和连续任务处理，是系统的核心业务模块。  
3. 多模态输入模块：负责文本输入、文件上传、短录音转写和长音频任务接入，使不同类型信息进入统一工作流链路。  
4. 历史会话管理模块：负责历史会话的展示、查询、重命名、删除、置顶和分享，支撑结果沉淀与复用。  
5. 用户配置与身份管理模块：负责登录、注册、密码重置、用户偏好设置、快捷提示词配置和长期记忆管理。

**图4 功能模块结构图（建议绘制）**  
`主界面导航与任务触发 / 工作流处理 / 多模态输入 / 历史会话管理 / 用户配置与身份管理`

### 1.4 数据流转设计

系统数据流转以工作流会话为中心。用户在手机端输入文本、文件或语音后，前端先完成本地采集与必要缓存，再调用工作流接口上传到服务端。服务端完成内容处理后，将结果写入当前会话，并同步更新历史摘要、任务状态或用户偏好相关数据。前端收到返回结果后更新界面，并在本地缓存会话内容以提高再次访问速度。

该设计强调三个关键点：

1. 缓存：手机端缓存当前会话、历史摘要和部分用户配置，以提升交互流畅度。  
2. 同步：关键业务数据通过接口同步到服务端，由服务端统一保存和管理。  
3. 异步任务：长音频等处理时间较长的任务通过任务轮询机制保持状态同步。

**图5 数据流转流程图（建议绘制）**  
`文本/文件/语音 -> 前端采集 -> 工作流接口 -> 后端处理 -> 会话/历史/偏好读写 -> 前端展示`

### 1.5 用户界面设计

区域赛阶段的用户界面设计主要围绕核心功能模块展开，重点提供以下几类运行界面：

1. 首页界面：用于展示快捷能力入口、录音触发区域以及门户信息，是任务触发的重要界面。  
2. 工作流界面：用于展示工作流消息块、输入栏、录音状态、附件和结果内容，是任务处理的核心界面。  
3. 历史界面：用于展示历史会话列表及其管理操作，包括搜索、重命名、删除、置顶和分享。  
4. 用户配置/认证界面：用于完成登录、注册、密码重置和偏好设置，支撑个性化服务。

界面设计以移动端操作习惯为基础，强调页面切换清晰、输入方式统一、任务结果连续可见。

### 1.6 数据结构设计

本项目数据结构设计以核心业务对象为主，不展开数据库表设计。主要对象如下：

1. 用户信息：包括用户标识、昵称、手机号和认证状态。  
2. 工作流会话：用于标识一次完整任务处理过程，包括会话编号、更新时间和关联内容。  
3. 消息块：包括用户输入块和 AI 响应块，是工作流展示和处理的基本单位。  
4. 文件/音频资源：包括文件引用、音频资源编号、音频时长和转写结果。  
5. 历史会话摘要：包括会话标题、预览文本、更新时间和置顶状态。  
6. 用户偏好：包括预设模式、快捷提示词和长期记忆内容。  
7. 长音频任务：包括任务编号、任务状态和处理结果。

这些核心对象共同支撑系统的输入采集、任务处理、会话管理和历史沉淀。

### 1.7 接口设计

#### 1.7.1 外部接口

系统外部接口包括软件接口和硬件接口两类。

软件接口方面，系统可调用 DeepSeek API 处理复杂文本任务，调用 Ollama 和 Whisper 等本地模型服务完成本地推理与语音转写，并通过 PostgreSQL 和 ChromaDB 支撑数据存储与语义存储。  
硬件接口方面，手机端主要调用麦克风接口进行录音，调用文件访问接口进行文件选择与上传，并调用本地存储接口保存会话和用户配置。

这些外部接口共同支撑了系统的输入采集、模型推理和数据管理能力。

#### 1.7.2 内部接口

系统内部接口主要分为前后端 REST 接口和前端内部模块接口。

前后端 REST 接口包括认证接口、工作流接口、历史记录接口、用户偏好接口和门户数据接口。它们负责完成数据提交、结果获取、状态同步和会话管理。  
前端内部模块接口主要包括页面与服务层的调用接口、录音与上传服务接口、历史存储接口以及会话管理接口。这些接口用于组织前端页面逻辑、管理本地缓存并协调与后端的交互。

接口详细定义可结合现有 `api doc.md` 继续补充。

### 1.8 错误/异常处理设计

#### 1.8.1 错误/异常输出信息

系统采用统一响应格式：

- 成功：`{ code: "0", message: "ok", data: ... }`
- 失败：`{ code: "ERR_xxx", message: "...", details?: {...} }`

典型错误包括参数错误、会话不存在、任务不存在和系统内部错误等。

#### 1.8.2 错误/异常处理对策

针对运行过程中可能出现的异常，系统采取以下处理对策：

1. 前端在请求失败时给出明确提示，并在必要时回退到安全状态。  
2. 对长任务采用轮询与超时处理，避免用户长时间无反馈。  
3. 对部分处理链路提供 mock 或降级结果，以保证演示阶段流程可继续运行。  
4. 当服务恢复后，系统可通过重新提交请求或重新拉取会话内容实现恢复。

### 1.9 系统配置策略

系统配置主要包括前后端接口地址、本地缓存键名、用户配置项、模型接入方式以及开发与演示环境切换策略。开发环境下可直接连接本地后端与调试服务，演示或部署环境下可通过修改接口地址和模型接入配置切换到目标环境。该策略能够保证系统在不同运行环境中的可配置性与可迁移性。

### 1.10 系统部署方案

本项目采用“手机端轻量部署 + 后端服务集中部署”的部署方案。手机端可通过 Expo Go 进行开发调试，也可打包为 APK 安装到 Android 设备中。后端通过 Python/FastAPI 服务运行，也可借助 Docker Compose 部署数据库、向量库和后端服务。模型服务与数据库均部署在服务端，不在手机端运行，从而降低对手机性能的依赖。

### 1.11 跨端应用架构设计

当前项目的跨端架构重点不是多终端产品协同，而是手机端与服务端之间的协同设计。系统通过 HTTP/JSON 协议完成手机端与服务端的数据通信，以统一响应格式 `{ code, message, data }` 组织接口结果，并通过会话 ID 作为任务主线标识。针对历史模块与工作流模块中 `id/sessionId` 的兼容写法，系统内部保持统一映射规则，以保证不同模块对同一会话的协同处理能力。

该设计为后续扩展到更多终端保留了接口基础，但当前阶段重点仍为手机端与服务端之间的协同。

### 1.12 其他相关技术与方案

本项目已采用的相关技术与方案主要包括：

1. React Native 与 Expo：用于移动端界面与交互实现。  
2. FastAPI：用于后端接口与业务服务构建。  
3. AsyncStorage：用于手机端本地缓存和状态持久化。  
4. PostgreSQL 与 ChromaDB：分别用于结构化数据和语义数据存储。  
5. 本地模型与云端模型混合调用：用于平衡性能、成本与处理能力。  
6. 异步任务机制与本地缓存策略：用于支撑长音频处理和会话连续性。

这些技术共同构成了系统当前阶段的实现基础，并为后续扩展提供支撑。
