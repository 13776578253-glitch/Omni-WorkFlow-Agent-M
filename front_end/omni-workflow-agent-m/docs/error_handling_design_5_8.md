## 5.8 错误/异常处理设计

本节围绕系统运行过程中可能出现的错误与异常情况展开说明，重点描述系统如何以统一格式输出异常信息，以及在前端、本地缓存、异步任务和后端接口等环节中如何进行处理与恢复。整体设计强调错误输出的一致性、任务处理的连续性以及移动端场景下的可恢复性，避免单点异常直接中断整条工作流链路。

结合当前代码仓库实现，系统在服务端采用统一响应格式封装成功与失败结果，在前端通过接口层抛错、页面层回退、本地缓存兜底和异步任务状态轮询等方式维持稳定交互。该设计适用于移动端网络波动、输入失败、任务超时、资源不存在等典型场景。

### 5.8.1 错误/异常输出信息

系统采用统一的接口输出格式组织运行结果。正常情况下，服务端返回：

- 成功：`{ code: "0", message: "ok", data: ... }`
- 失败：`{ code: "ERR_xxx", message: "...", details?: {...} }`

上述格式由后端公共响应结构统一定义，其中 `code` 用于标识结果类型，`message` 用于提供简明说明，`data` 用于承载正常业务结果，`details` 用于在必要时补充异常细节。当前后端通过公共响应封装函数、统一异常处理逻辑以及各路由中的异常抛出机制，保证不同接口域在错误表达上的一致性。

结合现有代码与测试覆盖，系统中的典型错误/异常输出可归纳为以下五类：

1. 参数校验异常  
   当请求缺少必要字段、字段类型不合法或请求格式不符合接口要求时，系统统一返回 `ERR_VALIDATION`，用于提示调用方修正输入内容。

2. 身份与用户异常  
   当登录用户不存在、密码校验失败或目标用户信息缺失时，系统会返回 `ERR_AUTH_USER_NOT_FOUND`、`ERR_AUTH_INVALID_PASSWORD` 或 `ERR_USER_NOT_FOUND` 等错误码，用于区分认证失败与用户资源缺失两类场景。

3. 会话相关异常  
   当工作流请求缺少 `sessionId`、`sessionId` 与 `id` 不一致、或目标工作流会话不存在时，系统会返回 `ERR_WORKFLOW_SESSION_REQUIRED`、`ERR_WORKFLOW_SESSION_MISMATCH`、`ERR_WORKFLOW_SESSION_NOT_FOUND`，用于保证工作流主线的一致性和可追踪性。

4. 历史与任务异常  
   当历史会话不存在或长任务状态查询目标不存在时，系统会返回 `ERR_HISTORY_SESSION_NOT_FOUND` 或 `ERR_WORKFLOW_TASK_NOT_FOUND`，用于提示目标资源已失效或无法访问。

5. 系统内部异常  
   当服务端出现未预期错误或内部处理异常时，系统统一返回 `ERR_INTERNAL`。该类异常用于兜底处理非业务型故障，避免前端接收到无结构的错误结果。

在前端侧，接口层会对非成功响应、响应格式错误或缺少必要字段等情况直接抛出异常，由页面层或服务层根据具体场景决定提示、回退或继续使用已有数据。该机制使前端能够以统一方式感知后端错误，而不需要对每个接口分别设计异常协议。

### 5.8.2 错误/异常处理对策

系统在错误/异常处理上采用“前端及时感知、本地状态兜底、异步任务持续反馈、后端统一封装”的协同策略，以保证移动端工作流在出现局部异常时仍可维持基本可用。

#### （1）前端接口层处理

前端 API 调用层在接收服务端响应后，首先判断响应内容是否为合法 JSON、是否包含统一结果结构、以及返回码是否为成功状态。若接口返回格式不合法、缺少 `data` 字段或返回错误码，前端会直接抛出异常，由上层页面逻辑统一处理。该策略已在工作流、认证、历史记录和用户偏好等接口中保持一致，能够有效避免无效响应继续向界面层传播。

对于工作流主链路中的生成、附件上传、录音转写和长任务提交等高频操作，前端在发生异常时会优先中止当前请求，并由页面层根据上下文决定后续行为，从而保证错误被及时识别，不会 silently 覆盖有效状态。

#### （2）前端本地缓存与静默回退

在移动端场景下，系统通过本地缓存优先和静默回退机制保障交互连续性。工作流页面在恢复会话时优先读取本地缓存，若远端会话拉取失败，则继续使用本地数据进行展示；历史记录和用户偏好模块在远端同步失败时，也会保留本地数据并静默回退，以避免界面内容整体失效。

对于结果生成和语音输入等链路，系统在必要时保留回退内容。例如，工作流生成失败时可回填备用结果块，短录音转写失败时可回退到默认转写文本，长音频任务异常时可使用回退内容完成当前工作流界面的连续展示。该类处理不改变系统主链路设计，但能够在比赛演示与弱网环境下增强稳定性。

#### （3）长任务与异步处理

长音频等耗时任务采用异步任务处理机制，并通过状态查询接口维持用户感知。系统在任务创建后生成 `taskId`，前端通过轮询方式持续获取 `pending`、`processing`、`completed` 或 `failed` 等状态变化。当任务长时间未完成或查询失败时，前端不会立即中断整个工作流页面，而是通过等待、重查或回退结果等方式保持界面可用。

该设计能够将即时交互与长时任务解耦，避免单次长任务阻塞整条会话链路，同时也为后续恢复、重试和结果补齐保留接口基础。

#### （4）后端统一异常封装与恢复策略

后端在异常处理上采用统一封装机制。各路由在识别到参数错误、资源缺失、会话不一致或任务不存在时，通过 `HTTPException` 配合统一错误结构输出对应错误码；对于请求校验失败，系统统一输出 `ERR_VALIDATION`；对于未捕获的内部异常，系统统一输出 `ERR_INTERNAL`。这一策略能够保证不同接口域对外暴露的异常格式一致，便于前端统一处理。

在恢复策略上，系统优先保证核心业务链路的可继续性。对于可重试请求，可通过重新提交或重新拉取会话详情恢复；对于本地已有有效状态的场景，优先保留当前界面与缓存数据；对于长任务场景，通过再次轮询或后续补拉结果实现状态恢复。整体上，系统并不依赖重型容灾机制，而是通过统一异常输出、前端回退、本地缓存和状态回查等方式形成适合移动端应用的轻量异常处理体系。
