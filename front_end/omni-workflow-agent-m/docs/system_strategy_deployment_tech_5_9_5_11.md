## 5.9 系统配置策略

本节围绕系统在开发、调试、演示和部署过程中的配置组织方式展开说明，重点描述前后端接口地址、本地缓存键名、服务端环境变量、数据源策略和运行环境切换方式。配置策略的目标是在保证系统主链路稳定运行的前提下，使移动端前端、后端服务和底层数据支撑能够根据不同环境完成快速切换与统一协同。

结合当前代码仓库实现，系统配置主要分为手机端配置和服务端配置两部分。手机端配置集中体现在接口基础地址、本地缓存键和页面状态持久化策略上；服务端配置集中体现在数据库地址、日志路径、第三方服务密钥和数据源策略等内容上。该设计便于在本地开发环境、演示环境和后续扩展环境之间进行平滑迁移。

### 5.9.1 前端配置策略

前端配置以统一 API 基地址和本地缓存键名为核心。当前前端通过 `auth-api.ts`、`history-api.ts`、`workflow-api.ts`、`personal-api.ts` 等接口层模块统一访问 `http://localhost:8000/api`，从而保持不同功能页面在调用后端时的一致性。该方式使前端能够通过集中修改接口基础地址的方式快速切换目标后端环境。

本地配置数据主要通过 `AsyncStorage` 进行持久化，涉及认证状态、当前工作流会话、工作流消息块、历史记录、用户偏好和主题模式等内容。系统使用固定的本地键名组织这些状态，如用户认证信息键、工作流用户数据键、当前会话键和历史存储键等，以保证前端在页面切换、应用重启和弱网场景下仍能恢复核心状态。

### 5.9.2 后端配置策略

后端配置通过集中配置文件与环境变量共同完成。系统在 `config.py` 中统一管理日志目录、数据库地址、第三方服务密钥和数据源策略，并支持通过 `.env` 文件覆盖默认配置。当前默认数据库地址采用本地 PostgreSQL 连接方式，同时兼容容器环境中的数据库地址重写，从而保证本地直连与容器部署两种运行模式都能正常使用。

对于底层数据来源，系统采用数据源策略机制组织不同模块的运行方式。后端支持 `mock_only`、`db_preferred_with_mock_fallback`、`db_only` 等策略，并允许按认证、偏好、历史、工作流、门户和文件音频任务等模块分别配置。该策略使系统能够根据比赛演示、功能调试和真实数据接入需求灵活选择合适的数据来源模式。

### 5.9.3 配置切换原则

系统配置切换遵循“前端地址统一、后端环境集中、缓存键保持稳定、数据源按模块可调”的原则。开发环境下可采用本地 Expo 调试配合本地 FastAPI 服务运行；演示或部署环境下则可通过修改 API 基地址、数据库连接地址和数据源策略，将系统切换到目标后端与底层服务环境。通过这种方式，系统既能保持开发阶段的灵活性，也能保证部署阶段的可迁移性和可维护性。

## 5.10 系统部署方案

本项目采用“手机端轻量部署、服务端集中处理”的部署方案。移动端负责界面展示、数据采集、录音和文件输入、本地缓存及用户交互，后端负责认证、工作流处理、历史管理、偏好管理、长任务维护以及模型与数据库接入。该方案能够降低手机端对算力和存储资源的依赖，使系统更适合在普通移动设备上运行。

### 5.10.1 手机端部署方式

手机端采用 Expo 与 React Native 技术栈实现，支持两类部署方式。开发阶段可通过 `expo start` 配合 Expo Go 直接在真机上运行，便于调试页面交互、接口通信和多模态输入能力；演示阶段可通过构建 Android 安装包的方式，将系统部署到真实设备中完成离线安装与展示。

在端侧部署中，手机不承担模型推理和复杂任务处理，仅负责用户输入采集、页面展示、会话缓存和结果回显。前端通过 HTTP API 与后端服务通信，无需在手机端本地部署数据库、向量库或模型服务，从而降低了部署复杂度。

### 5.10.2 后端部署方式

后端采用 FastAPI 实现统一服务入口，通过 `/auth`、`/user`、`/history`、`/portal`、`/workflow` 五类接口域对前端提供能力。部署时既可直接在本地 Python 环境中使用 `uvicorn` 启动服务，也可借助仓库中的 `docker-compose.yml` 统一部署后端、PostgreSQL 和 ChromaDB。该方式便于在开发、联调和演示阶段快速完成环境搭建。

在容器部署方案中，系统将 PostgreSQL、ChromaDB 和后端服务分别组织为独立容器，并通过环境变量注入数据库地址和底层服务地址。该设计使系统能够在单机环境中完成完整演示，也为后续扩展到更稳定的服务器环境保留了基础。

### 5.10.3 部署组织特点

系统部署方案体现出三个特点。第一，端侧轻量，手机主要负责交互和采集，不承担高负载处理；第二，服务端集中，工作流、历史、偏好、音频处理和数据管理统一在后端完成；第三，底层支撑可扩展，数据库、向量库和模型服务可根据环境逐步替换或增强。整体上，该方案兼顾了比赛项目的可实施性、演示稳定性和后续扩展空间。

## 5.11 其他相关技术与方案

除前述配置与部署设计外，系统还采用了一系列与移动端 AI 工作流场景相适配的关键技术与实现方案，用于支撑界面交互、状态管理、多模态输入、异步处理和后续扩展能力。

### 5.11.1 前端技术方案

前端采用 React Native 与 Expo Router 构建移动端应用，通过页面路由、组件化结构和原生能力接入实现首页、工作流页、历史页和用户页等核心界面。系统结合 `AsyncStorage` 完成本地状态持久化，并通过录音、文件选择、图片选择和分享等 Expo 能力补充移动端多模态交互方式，使手机端既保持轻量，又具备较完整的输入与展示能力。

### 5.11.2 后端服务方案

后端采用 FastAPI 构建接口服务，并通过统一路由域、统一响应结构和统一异常封装组织业务能力。系统在工作流、历史、用户偏好和门户等场景中使用结构化接口设计，使移动端能够以一致方式访问后端服务。同时，后端保留数据源策略和模块化处理路径，为不同阶段的数据接入方式和服务演进提供支撑。

### 5.11.3 数据与智能能力方案

在数据支撑方面，系统采用 PostgreSQL 管理结构化业务数据，采用 ChromaDB 预留语义向量存储能力，并结合本地缓存机制提升移动端会话恢复与历史回显速度。在智能能力方面，系统采用本地模型服务与云端模型服务混合接入的方案：本地能力用于承接语音识别或部分就近处理需求，云端能力用于补充复杂文本生成与长上下文处理能力。该组合方式有助于在性能、成本和结果质量之间取得平衡。

### 5.11.4 异步与连续性交互方案

为适应长音频和复杂工作流任务，系统采用异步任务与本地缓存协同的处理方案。长时任务通过状态查询机制维持前端可感知性，普通输入则通过即时回填保证交互响应。与此同时，系统在工作流、历史和偏好等模块中保留本地优先恢复与服务端同步机制，从而增强在移动端环境下的连续使用体验。

总体而言，这些相关技术与方案共同构成了系统当前阶段的实现基础，使项目在移动端交互、多模态输入、服务端处理、数据存储和能力扩展等方面具备较好的完整性与可延展性。
